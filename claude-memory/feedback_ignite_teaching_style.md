Rules learned across [[project-ignite-learning-mission]] sessions, confirmed as standing habits (not one-off requests):

- **Give a same-day agenda up front before diving into a new topic**, and let basic terms land one at a time before adding context/detail on top of them. Why: explicitly requested twice during Topic 9 Day 1 (Docker) after context was introduced too early alongside term definitions. How to apply: at the start of each teaching block, state the plan for the session in a line or two, then introduce terms bare before connecting them to real command output or architecture.

- **Never assume outside tech knowledge, and explain every new term proactively, unprompted — the moment it's introduced, not only when asked.** Why: explicit feedback in session 12 after an explanation assumed unstated background, reinforced again in Topic 10 when the user had to explicitly ask for a plain "what is a volume?" definition before continuing a hands-on step, and pointed to Topic 9's notebook (how "image"/"container"/"registry" etc. were defined from scratch before being used) as the standard to match by default, without needing to be asked. How to apply: treat the user as a total beginner (their words: "like dealing with a school kid") by default — before using ANY new term for the first time in a session, stop and define it plainly in a sentence or two, the way Topic 9's notebook models it, rather than waiting for a follow-up question.

- **When an explanation isn't landing after ~1-2 tries, switch to "run it and watch real output" rather than a third or fourth variation of the same kind of verbal explanation.** Why: function scoping (Topic 3) didn't land through multiple analogies but clicked almost immediately once a real script printed `$1` at three points and the user watched actual values. How to apply: for the 2nd re-teach attempt especially, prefer a live, concrete, observable demonstration over another abstraction/analogy.

- **Redact the real employer name from anything in `learning/notes/`** (the study notebooks). Why: explicit privacy request in session 12. How to apply: verified clean as of 2026-07-24 — no employer name found in `learning/notes/`; keep checking newly written notebook content before it's saved.

- **Don't turn Socratic hinting into a guessing game once the user has honestly said "I don't know."** Explicitly corrected during Topic 10 (Docker networking, why 3 IPs show "in use" on an empty bridge network) after two hint rounds on a concept never actually taught yet (network/gateway/broadcast address reservation). Why: pushing a second or third guess at something outside what's been explicitly covered reads as assuming background knowledge, not testing it — the user wants to be treated as knowing only what's actually been taught so far, nothing inferred. How to apply: one light nudge is fine, but as soon as the user says they genuinely don't know, stop fishing and just explain the concept plainly and directly, grounded in only prior covered topics — don't require them to infer brand-new terminology from clues.

- **Pick whatever analogy actually lands for the user per topic, not whatever was used in an earlier topic's notes.** During Topic 10, the user preferred the roads/bridge analogy over reusing Topic 5's mail analogy for networking, and said explicitly: use different examples for different sessions rather than forcing one running analogy framework across topics. How to apply: it's fine, even good, for notebook analogies to vary topic-to-topic — don't manufacture false consistency with earlier topics unless the user reaches for that connection themselves.

- **State the exact working directory/location for every single command given, every time, not just when a path is technically ambiguous.** Why: explicit standing request during Topic 10's volumes exercise ("tell me everytime from which location i need to run the commands") after being unsure where a relative `mkdir` should be run relative to an absolute Docker path. How to apply: prefix or label every command block with the folder it should be run from (e.g. "From `C:\CloudOps\ignite\project`:"), even for commands that seem obviously run from "wherever you already are."

- **Don't re-explain a topic's motivation/preamble from scratch every time a side-tangent interrupts and the conversation returns to it.** Corrected in Topic 10 after re-introducing "why Docker Compose exists" three separate times, once per return from an interrupting side-check (an OCD-driven cleanliness audit, a container rename, etc.), instead of just picking back up at the actual next hands-on step. Why: the user had already understood and engaged with the explanation the first time; repeating it read as not tracking what had already landed. How to apply: after any tangent, resume from the concrete next action (the next command, the next file to write), not from the topic's opening rationale — a one-line "picking back up where we left off" is enough context, not a full re-explanation.

- **After explaining or completing any concept/step, explicitly ask "shall I move to the next concept?" and then actually WAIT for an explicit "yes"/"proceed" reply before starting the next one — never ask and continue in the same turn.** Why: explicit standing request in Topic 10, refined a second time after the first version still bundled the next step's content into the same message as the question. As a genuine fresher, the user needs a clear, reliable pause point to ask questions about the concept just covered before it's left behind; asking-then-immediately-continuing defeats the purpose. How to apply: end a turn on the checkpoint question itself, with nothing beyond it — no preview of the next step, no "or if yes, here's what comes next." Only after a real explicit affirmative reply, proceed. Silence or an unrelated reply is NOT permission to continue.

- **Annotate hands-on code (any config/code shown for a hands-on exercise, any topic, going forward) with inline structural comments explaining what each non-obvious line/indentation level means** — e.g. `← indented, belongs to "app"` / `← NOT indented, belongs to nothing above it — it's its own section`. Why: explicit standing request during Topic 10's Docker Compose section, after two `volumes:` keys at different indentation levels in the same YAML file meant two completely different things, and plain-prose explanation alongside the block wasn't as immediately clear as inline annotation pointing at the exact line. How to apply: applies to all future topics' hands-on code/config, not just YAML — whenever a line's meaning depends on its position, nesting, or indentation (not just what it says), annotate that specific line directly rather than only explaining it in surrounding prose.
