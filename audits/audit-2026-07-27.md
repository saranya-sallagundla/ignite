# Repo Audit — after Topic 10 (before Topic 11)

**Date**: 2026-07-27 · **Scope**: every file in the repo (root files, all `learning/` files, all
10 notebooks, all `orbit/` files, git history/hygiene) · **Method**: a 17-agent audit (12
parallel workflow auditors covering different files/dimensions + 5 dedicated notebook auditors,
since the first pass of notebook auditors stalled on the larger files and had to be re-run in
smaller batches — worth remembering for the next audit: split large-file auditors into 2-file
batches, not 4-file, to avoid agent stalls).

> **Title vs. date, explained.** "before Topic 11" describes this audit's *scope* — it covers the
> repo as it stood once Topic 10 cleared, before Topic 11's work began — not a calendar claim.
> This audit's own date (07-27) falls after Topic 11's session-log date (07-24) because both were
> authored during the same catch-up period; see the pacing gap `audit-2026-08-13.md`'s finding
> C-7 documents. Neither date has been altered to make the two agree.

**Overall result going in**: fundamentally strong — clean linear git history, no secrets ever
committed, one consistent author identity, scores/session counts consistent across files, no
employer name in 28 of 29 files. What surfaced was real, though: 4 critical items, ~30 important,
and a long tail of minor/cosmetic consistency issues. All were reviewed with the user before any
fix was applied, then fixed in 8 separate, reviewable, individually-committed batches.

---

## Batch 1 — Critical (4 items)

1. **Employer org name in `orbit/docs/concept.md`** — the actual employer name appeared directly
   in file content (as part of a GitHub org reference). *Why it matters*: house rule (now in `CLAUDE.md`) forbids the employer name in
   any file content, in any casing — this is the one rule with zero tolerance, since it's the
   difference between a personal project and an accidental leak of employer affiliation.
2. **`orbit/README.md`'s "How to run it" section said there was nothing to run**, directly
   contradicting the Status section two lines below it (which said the app runs via Compose).
   *Why it matters*: this is the first thing a reviewer reads in the showcase folder — a
   self-contradiction there undermines trust in everything else in the repo.
3. **Topic 3 notebook taught a bash syntax rule backwards** (claimed `else echo "..."` was invalid
   and `else; echo "..."` was the fix — the reverse of the truth). *Why it matters*: this is a
   technical reference document; a factually wrong rule taught as a lesson actively miseducates
   anyone who reads it, including future-you.
4. **Topic 7 notebook had an unescaped backtick that broke Markdown rendering on GitHub**. *Why it
   matters*: broken rendering is immediately, visibly wrong to anyone opening the file — no reading
   required to notice something's off.

## Batch 2 — Repo hygiene

Added a root `.gitignore`, root `.gitattributes` (normalizes line endings to LF, fixing the
recurring CRLF warnings), and `orbit/app/.dockerignore`. Also fixed the root README's ASCII
repo tree (missing `docker-compose.yml`, a one-space misalignment).

*Why it matters*: a DevOps-focused repo with no `.gitignore`/`.dockerignore` reads as a missed
fundamental to exactly the kind of reviewer this project is meant to impress — these are the
first files a technically literate person checks for.

## Batch 3 — Showcase polish (`orbit/`)

- Renamed `orbit/README.md`'s title from the generic "The project" to "Orbit — DevOps
  Capstone Project," matching the project's actual identity elsewhere.
- Rewrote `orbit/app/README.md` to drop internal-scaffolding language ("not yet defensible in an
  interview," a direct reference to `CLAUDE.md`) that had leaked into the interview-facing folder.
- Cleaned `docker-compose.yml`: removed line-by-line teaching comments and a leftover two-service
  demo (`app2` + an unused shared volume) that served no purpose beyond the lesson it came from.
- Reworded `docs/concept.md`'s framing away from language that reads oddly to an employer reviewer
  (planning around "the org repo being deleted," anchoring the demo to "onsite interviews"), and
  corrected a wrong GitHub Codespaces quota figure (120 core-hours, not 60).
- Normalized all 5 placeholder READMEs (`k8s/`, `terraform/`, `ansible/`, `monitoring/`,
  `scripts/`) to one consistent, correctly-tensed template.

*Why it matters*: `orbit/` is explicitly the folder meant to be shown in an interview — every
item here was something that would read as unpolished, inconsistent, or (worse) revealing to
exactly the audience this repo is built for.

## Batch 4 — Learning-file consistency

Normalized topic names to one canonical form (the em-dash form from `roadmap.md`'s fixed
baseline) across `progress.md`, `roadmap.md`, `handbook_status.md`, and notebook titles — topic
names had drifted into commas, slashes, and colons in different places. Fixed a self-contradictory
technical claim about Docker's `:latest` tag, several casing/formatting inconsistencies in
`progress.md`, and softened `CLAUDE.md`'s 20-minute quiz cap wording so it no longer directly
contradicted the (correctly logged) real overruns.

*Why it matters*: a reviewer who cross-references two files and finds the same topic named three
different ways, or a stated rule contradicted by the very next log entry, reasonably wonders what
else doesn't line up — consistency is what makes the tracking system credible as a real record
rather than a loosely-maintained diary.

## Batch 5 — Notebook technical accuracy

Fixed real technical errors across all 10 notebooks — each one independently verified, not just
reworded. Highlights: the SSH authentication mechanism was described as encrypted-challenge when
real SSH key auth is signature-based; `/etc/fstab` was twice said to be read by "the kernel" at
boot (it's the init system, systemd); a "No route to host" explanation blamed a router for a
destination that was actually on the same local subnet (the real cause is a local ARP failure); a
GitHub Actions claim said secrets always appear in logs (Actions auto-masks registered secrets by
default); and Topic 10 had a few internal-timeline inconsistencies (an anecdote placed on the
wrong day, a redundant command contradicting its own surrounding explanation).

*Why it matters*: these notebooks are the actual technical reference — if someone (including
future-you, prepping for a real interview) trusts a wrong rule recorded here, it fails at exactly
the moment it's relied on.

## Batch 6 — Final cosmetic sweep

Wording fixes in `session_notes.md` (terminology drift, a hyphenation error, unformatted inline
commands), a redundant word pair in `progress.md`, quiz-heading punctuation normalized across
notebooks, a missing separator and two mislabeled code fences in Topic 10, trailing newlines
added to `Dockerfile` and `app/README.md`.

*Why it matters*: individually trivial, but a repo covered in small inconsistencies reads as
careless in aggregate even when no single item matters much on its own.

## Batch 8 — Date/time normalization

Standardized every session/Day heading across `progress.md`, `session_notes.md`,
`orbit/README.md`, and 8 notebooks to show only the day the session/day *started* (not a date
range) — some headings showed a range when a session crossed midnight IST, others didn't, with no
consistent rule for when. Spelled out an ambiguous date shorthand in the light-days log. Added a
one-line note explaining that raw command output and git commit metadata reflect the machine's
real local clock (US Eastern), not the IST convention used for narrative dates, so a reviewer
doesn't mistake that expected difference for an inconsistency.

**Explicitly verified**: every Check-in/Check-out timestamp, in every file, was left completely
untouched by this batch — confirmed via `git diff` showing zero lines added or removed on any
Check-in/Check-out line. *Why this matters*: those lines are the one part of this repo whose
entire value depends on being real, uninvented data — the pacing math, the "am I on track for 6
months" answer, all of it is computed from them.

## Follow-up fix (post-audit, same day)

Topics 9 and 10 were missing the descriptive content-summary parenthetical that every other
notebook's Day heading carries (e.g. Topic 3 Day 2: `(loops, functions, exit codes — quiz
deferred on functions)`) — Topic 9/10's Day 2 just said `(final day)` with no content summary, and
Day 1 had nothing. Added matching summaries to all 4 headings, and fixed Topic 10's H1 title,
which was missed during the em-dash normalization pass. *Why it matters*: a reader scanning the
table of contents for a specific topic's Day 1 vs. Day 2 content relies on this summary to jump to
the right place without opening the file.

## Deferred — Batch 7 (intentionally NOT fixed in this audit)

A set of `Dockerfile`/`docker-compose.yml` improvements that are exactly Topic 11's subject
matter (Docker: Multi-Stage Builds & Best Practices), so they're saved for when that topic is
actually taught rather than fixed retroactively:

| Item | Why it matters |
|---|---|
| Container runs as root (no `USER` instruction) | Standard container-security flag any reviewer or scanner checks first |
| Flask's dev server used in the container (`CMD ["python","app.py"]`) | Not production-grade; prints a dev-server warning on every start |
| Missing `EXPOSE 5000` | Documents which port the container uses |
| Missing `HEALTHCHECK` despite a purpose-built `/health` endpoint | Nothing currently consumes the endpoint that exists for exactly this |
| `pip install` without `--no-cache-dir` | Bloats the image with an unneeded download cache |
| Missing `PYTHONUNBUFFERED=1` | Python buffers stdout in containers by default; logs can lag during a demo |
| Compose builds an untagged image | `orbit/README.md` claims the image is "properly version-tagged"; the compose file doesn't back that up yet |
| `flask==3.1.0` slightly behind a security-patched `3.1.1` | Low real risk here, but a dependency scanner would flag the pin |

**Next audit should confirm these were actually addressed during Topic 11**, not still sitting
here unresolved.
